= Ansible Automation for OpenShift Virtualization

== Introduction

The Ansible Automation section covers how to automate virtual machine lifecycle management, configuration, and day-to-day operations using Red Hat Ansible Automation Platform (AAP). Ansible enables you to automate repetitive tasks, enforce consistency across VM deployments, and scale operations efficiently.

This module enables organizations to:

* Dynamically discover and inventory OpenShift-based VMs
* Automate VM provisioning, configuration, and deprovisioning
* Execute patching campaigns across multiple VMs
* Perform dynamic resource allocation (hot-plugging)
* Monitor VM health and performance
* Create self-service workflows for developers
* Reduce manual operational overhead

.*What You'll Learn*

* Create dynamic inventory from OpenShift Virtualization workloads
* Build Ansible playbooks for VM lifecycle automation
* Automate patch management workflows
* Dynamically add resources to running VMs with Ansible
* Monitor VM alerts, metrics, and logs
* Integrate with Ansible Automation Platform (AAP) controller
* Implement infrastructure-as-code for virtualization

.*Topics Covered*

. xref:04-day-to-day-ansible.adoc#dynamic_inventory[Dynamic Inventory] — Automatically discover and track OpenShift VMs
. xref:04-day-to-day-ansible.adoc#vm_mgmt_power[VM Lifecycle Automation] — Automate provisioning, configuration, and lifecycle
. xref:04-day-to-day-ansible.adoc[VM Patching] — Implement consistent patching strategies across environments
. xref:04-day-to-day-ansible.adoc#vm_mgmt_hp[Hot-Plug Automation] — Dynamically allocate resources with Ansible

== Module Overview

=== Dynamic Inventory (Module 04)

Dynamic inventory automatically discovers and tracks virtual machines in OpenShift Virtualization, eliminating manual inventory management.

*Key Features:*

* OpenShift Virtualization as inventory source in AAP
* Automatic VM discovery by namespace
* Dynamic host grouping by labels and namespaces
* Real-time inventory updates on every AAP job run
* Credential management for cluster access
* Variable assignment from VM metadata

*Topics Covered:*

* Creating an AAP inventory with OpenShift Virtualization source
* Configuring cluster credentials and authentication
* Setting up namespace filters and discovery scopes
* Executing inventory sync jobs
* Verifying discovered hosts
* Using dynamic inventory in playbooks

The dynamic inventory is the foundation for all subsequent automation workflows.

xref:04-day-to-day-ansible.adoc#dynamic_inventory[→ Go to Dynamic Inventory section]

=== VM Lifecycle Automation (Module 04)

Automate the complete lifecycle of virtual machines from provisioning through deprovisioning.

*Topics Covered:*

* Automated VM provisioning from templates
* Initial configuration via cloud-init
* Post-deployment configuration and hardening
* Health checks and validation
* VM deprovisioning and cleanup
* Error handling and rollback mechanisms

*Common Lifecycle Stages:*

1. **Request** — User or automation requests VM creation
2. **Provision** — VM deployed from template
3. **Configure** — Guest OS and applications configured
4. **Deploy** — VM placed into production
5. **Operate** — Ongoing monitoring and management
6. **Patch** — Security and OS updates applied
7. **Decommission** — VM and resources removed

Automation reduces time-to-production and ensures consistency.

xref:04-day-to-day-ansible.adoc#vm_mgmt_power[→ Go to VM Lifecycle Automation section]

=== VM Patching (Module 04)

Implement organized, repeatable patch management strategies for keeping VMs secure and current.

*Topics Covered:*

* Patch assessment and planning
* Pre-patch validation and backup
* Rolling patch deployments
* Kernel and OS package updates
* Application-specific patching
* Post-patch validation and testing
* Rollback procedures
* Compliance verification after patching

*Patching Strategies:*

* **Rolling Patches** — Patch one VM at a time for continuous availability
* **Canary Patching** — Test patches on a subset before full rollout
* **Maintenance Window** — Schedule patches during off-peak hours
* **Blue-Green Deployment** — Patch alternate environment, then switch

Efficient patching keeps systems current without disrupting services.

xref:04-day-to-day-ansible.adoc[→ Go to VM Automation section]

Hot-plug automation enables responsive infrastructure.

[[playbook_examples]]
== Common Playbook Patterns

=== Pattern 1: VM Provisioning Workflow

[source,yaml]
----
---
- name: Provision OpenShift Virtualization VM
  hosts: localhost
  vars:
    vm_name: production-db-01
    vm_template: rhel9-template
    vm_cpu: 4
    vm_memory: 8Gi
    namespace: vms-production
  tasks:
    - name: Create VM from template
      kubernetes.core.k8s:
        state: present
        definition: "{{ lookup('template', 'vm.yml.j2') }}"

    - name: Wait for VM to start
      kubernetes.core.k8s_info:
        kind: VirtualMachine
        name: "{{ vm_name }}"
        namespace: "{{ namespace }}"
      register: vm_status
      until: vm_status.resources[0].status.ready
      retries: 30
      delay: 10

    - name: Configure guest OS
      hosts: "{{ vm_name }}"
      tasks:
        - name: Update system packages
          yum:
            name: '*'
            state: latest
        - name: Install required packages
          yum:
            name: "{{ required_packages }}"
            state: present
----

=== Pattern 2: Rolling VM Patching

[source,yaml]
----
---
- name: Rolling patch deployment
  hosts: vm_group
  serial: 1  # Patch one VM at a time
  pre_tasks:
    - name: Drain workload
      command: drain_script.sh

  tasks:
    - name: Apply OS updates
      yum:
        name: '*'
        state: latest
      register: patch_result

    - name: Reboot if kernel updated
      reboot:
        msg: "Rebooting for kernel update"
        connect_timeout: 5
        reboot_timeout: 600
        pre_reboot_delay: 0
        post_reboot_delay: 30
      when: "'kernel' in patch_result.changes | string"

  post_tasks:
    - name: Health check
      command: health_check.sh
      register: health
      failed_when: health.rc != 0

    - name: Resume workload
      command: resume_script.sh
----

=== Pattern 3: Auto-Scaling Hot-Plug

[source,yaml]
----
---
- name: Auto-scale VM resources
  hosts: localhost
  tasks:
    - name: Get VM metrics
      community.vmware.vmware_guest_info:
        name: "{{ vm_name }}"
      register: vm_info

    - name: Hot-plug CPU if needed
      kubernetes.core.k8s:
        state: present
        definition:
          apiVersion: kubevirt.io/v1
          kind: VirtualMachine
          metadata:
            name: "{{ vm_name }}"
          spec:
            template:
              spec:
                domain:
                  cpu:
                    cores: "{{ new_cpu_count }}"
      when: current_cpu_utilization > 80

    - name: Hot-plug memory if needed
      kubernetes.core.k8s:
        state: present
        definition:
          apiVersion: kubevirt.io/v1
          kind: VirtualMachine
          metadata:
            name: "{{ vm_name }}"
          spec:
            template:
              spec:
                domain:
                  resources:
                    requests:
                      memory: "{{ new_memory_size }}"
      when: current_memory_utilization > 85
----

== Ansible Automation Platform Setup

=== Prerequisites for AAP Integration

* AAP Controller or Automation Hub installed
* OpenShift cluster with Virtualization installed
* Network connectivity from AAP to OpenShift API
* Service account with appropriate RBAC permissions
* Execution environment with OpenShift CLI and Python libraries

=== Initial Configuration Steps

1. **Create OpenShift Service Account**
   [source,bash]
   ----
   oc create serviceaccount aap-automation -n openshift-virt
   oc adm policy add-cluster-role-to-user cluster-admin \
     system:serviceaccount:openshift-virt:aap-automation
   ----

2. **Add Credential in AAP**
   * Navigate to *Credentials* in AAP Controller
   * Create *OpenShift Kubernetes* credential
   * Provide OpenShift API endpoint
   * Add service account token and CA certificate

3. **Create Dynamic Inventory**
   * Use OpenShift Virtualization plugin
   * Configure namespace filters
   * Set credential reference
   * Enable inventory sync

4. **Create Job Templates**
   * Reference dynamic inventory
   * Use execution environment with required libraries
   * Test with simple debug playbooks first

[[automation_best_practices]]
== Best Practices for VM Automation

=== Playbook Design
* Use roles to organize related tasks
* Implement idempotent operations
* Use handlers for service restarts
* Separate variables from logic
* Include comprehensive error handling

=== Inventory Management
* Keep inventory updated with VM metadata
* Use consistent naming conventions
* Tag VMs for easy grouping
* Document custom inventory variables

=== Execution Safety
* Test playbooks in staging first
* Use `--check` mode for dry-runs
* Implement approval gates for production
* Log all automation executions
* Create rollback procedures

=== Security
* Store credentials in Ansible Vault
* Use least-privilege service accounts
* Audit all automation activities
* Encrypt sensitive playbook variables
* Rotate credentials regularly

=== Scalability
* Use serial execution for rolling updates
* Implement parallelization where safe
* Monitor job execution times
* Optimize inventory queries
* Use cached facts to reduce queries

== New in OpenShift Virtualization 5.1

OpenShift Virtualization 5.1 introduces several new features and improvements that enhance VM operations, storage management, and cluster management. This section covers practical tasks you can perform with these new capabilities.

[[declarative_hotplug]]
=== Declarative Hotplug: Adding Resources Without VM Downtime

OpenShift Virtualization 5.1 graduates the Declarative Hotplug feature to General Availability (GA). This enables you to add or remove NICs (Network Interface Cards) and disks without stopping the VM.

*Task: Add a Disk to a Running VM Using Declarative Hotplug*

. Navigate to the Virtualization perspective and select your project
. Click on a running virtual machine to open its details panel
. Click the *Configuration* tab and select the *Storage* subtab
. Click the *Add disk* button
. In the Add disk dialog:
   * Provide a disk name (e.g., `data-disk-new`)
   * Select a size (e.g., 10 GB)
   * Choose a StorageClass from the dropdown
   * Click *Save*
+
image::exercise5/hotplug-disk-new.png[title="Add Disk to Running VM", link=self, window=blank, width=100%]

. The disk attaches immediately without stopping the VM. The VM guest OS detects the new device automatically.
. Log into the VM console to verify the new disk is available:
+
[source,sh,role=execute]
----
lsblk
----
. Format and mount the disk for use:
+
[source,sh,role=execute]
----
sudo mkfs.ext4 /dev/vdb
sudo mkdir /mnt/data
sudo mount /dev/vdb /mnt/data
----

*Task: Add a Network Interface to a Running VM*

. From the VM Configuration tab, select the *Network* subtab
. Click the *Add network interface* button
. In the Add network interface dialog:
   * Provide an interface name
   * Select a network attachment definition or pod network
   * Click *Save*
+
image::exercise5/hotplug-nic-new.png[title="Add NIC to Running VM", link=self, window=blank, width=100%]

. The interface is added immediately without VM downtime
. Verify the new interface in the VM guest OS:
+
[source,sh,role=execute]
----
ip link show
ip addr show
----

[[disk_serial_number]]
=== Disk Serial Number Management

OpenShift Virtualization 5.1 introduces GA support for managing disk serial numbers through the console. This is useful for tracking disks across migrations and ensuring VM portability across infrastructure platforms.

*Task: Configure Disk Serial Numbers for Migration Readiness*

. Open a virtual machine's Configuration tab and select *Storage*
. Click on an existing disk to edit it
. In the disk editor, you'll now see a *Serial number* field
. If migrating from VMware/vSphere, the disk serial number from the source VM UUID is automatically preserved:
+
[source,txt]
----
Source vSphere VM UUID: 421eef81-52f9-4f8d-8d4f-abc123def456
Preserved disk serial: vm-421eef81-52f9-4f8d-8d4f-abc123def456
----

. Assign meaningful serial numbers for tracking:
   * Use source infrastructure identifiers
   * Maintain consistency with naming conventions
   * Document the mapping for audits
+
image::exercise5/disk-serial-number.png[title="Disk Serial Number Management", link=self, window=blank, width=100%]

. Click *Save* to persist the serial number configuration

[[storage_class_migration]]
=== Storage Class Migration Improvements

OpenShift Virtualization 5.1 enhances storage class migration with better test infrastructure and improved UI, making it safer and easier to move VMs between storage tiers.

*Task: Migrate VM Storage to a Different StorageClass*

. Navigate to a running virtual machine's Configuration tab
. Click *Storage* to view attached disks
. Click on the disk you wish to migrate and select the *Migrate* action from the disk menu
. In the *Migrate Storage* dialog:
   * Select the *Destination StorageClass* from the dropdown
   * Review the migration plan (shows source and destination details)
+
image::exercise5/storage-migration-5-1.png[title="Storage Class Migration Dialog", link=self, window=blank, width=100%]

. Click *Migrate* to begin the operation
. Monitor the migration progress in the migration details panel:
   * Progress percentage
   * Estimated completion time
   * Any errors or warnings
. Once complete, verify the disk is using the new StorageClass:
+
[source,sh,role=execute]
----
oc get pvc -o wide
oc get storageclass
----

[[cloud_init_generator]]
=== Built-in Cloud-Init / Sysprep Configuration Generator

OpenShift Virtualization 5.1 includes a new built-in configuration generator in the console for cloud-init (Linux) and Sysprep (Windows) settings, simplifying VM customization during provisioning.

*Task: Configure Cloud-Init for a New Linux VM*

. When creating a new VM from the console, navigate to the *Customize* step
. In the *Initial run* section, you'll see a new *Cloud-Init Editor*
. Click *Open Editor* to generate cloud-init configuration:
+
[source,yaml]
----
#cloud-config
hostname: my-custom-vm
fqdn: my-custom-vm.example.com
users:
  - name: cloud-user
    sudo: 'ALL=(ALL) NOPASSWD:ALL'
    ssh-authorized-keys:
      - ssh-rsa AAAAB3NzaC...
packages:
  - git
  - curl
  - vim
package_update: true
package_upgrade: true
runcmd:
  - echo "VM Customization Complete"
----

. The editor provides syntax validation and common configuration templates
. Configure:
   * Hostname and FQDN
   * User accounts and SSH keys
   * Package installation lists
   * Custom initialization commands
. Click *Save* to apply the configuration
+
image::exercise5/cloud-init-generator.png[title="Cloud-Init Generator", link=self, window=blank, width=100%]

. Deploy the VM and verify the customization applied:
+
[source,sh,role=execute]
----
cat /etc/hostname
whoami
sudo apt list --installed | grep git
----

*Task: Configure Sysprep for a New Windows VM*

. When creating a new Windows VM, navigate to the *Customize* step
. In the *Initial run* section, select *Sysprep* from the dropdown
. Configure Windows VM settings:
   * Computer name
   * Administrator password
   * Time zone
   * Network configuration
. The generator creates the proper Sysprep answer file format
. Deploy the VM and Windows applies the configuration on first boot

[[network_qos]]
=== Network Quality of Service (QoS) Configuration

OpenShift Virtualization 5.1 enables VM network traffic shaping with Quality of Service policies, ensuring predictable network behavior for latency-sensitive workloads.

*Task: Configure Network QoS for a VM*

. Open a virtual machine's Configuration tab and select *Network*
. Click on a network interface to edit it
. In the network interface editor, you'll see new *QoS* settings:
   * *Egress bandwidth limit* — Maximum upload rate
   * *Ingress bandwidth limit* — Maximum download rate
+
image::exercise5/network-qos.png[title="Network QoS Configuration", link=self, window=blank, width=100%]

. Configure example values:
   * Set Egress limit: 100 Mbps (for controlled uploads)
   * Set Ingress limit: 500 Mbps (for controlled downloads)
. Click *Save* to apply the QoS policy
. From the VM console, test the bandwidth limits:
+
[source,sh,role=execute]
----
# Install iperf for bandwidth testing
sudo yum install -y iperf3

# On a test server, run: iperf3 -s
# On the VM, test upload speed:
iperf3 -c <test-server-ip> -R
# Test download speed:
iperf3 -c <test-server-ip>
----
. Monitor that traffic respects the configured QoS limits

[[mac_spoof_filtering]]
=== MAC Spoof Filtering Control

OpenShift Virtualization 5.1 allows administrators to enable or disable MAC spoof filtering on a per-network basis, supporting network architectures that require non-standard MAC addressing.

*Task: Disable MAC Spoof Filtering for an Appliance VM*

Appliance VMs or HA-cluster VMs may require multiple MAC addresses for failover. To support this:

. Navigate to the *Networking* section in the left menu under Virtualization
. Select *Network Attachment Definitions*
. Find or create a NAD (Network Attachment Definition) for your appliance network
. Edit the NAD configuration:
+
[source,yaml]
----
apiVersion: k8s.cni.cncf.io/v1
kind: NetworkAttachmentDefinition
metadata:
  name: appliance-network
spec:
  config: '{"cniVersion":"0.3.1","type":"ovn-k8s-cni-overlay","topology":"localnet","mtu":1400,"disableMACSpoofing":true}'
----

. Set `"disableMACSpoofing": true` in the CNI configuration
. Click *Save*
. Attach this network to your appliance VM:
   * Edit the VM configuration
   * Add a network interface
   * Select the appliance-network NAD
. The VM can now use multiple MAC addresses without filtering

[[vm_migration_progress]]
=== VM Migration Progress and Error Visibility

OpenShift Virtualization 5.1 displays migration operations in a dedicated modal with progress details and error information, reducing the need to check logs.

*Task: Monitor VM Migration with New Progress Modal*

. Start a live migration of a virtual machine:
   * Select a running VM
   * Click *Actions* > *Migration* > *Compute*
   * Choose a destination node and click *Migrate VirtualMachine*

. A new migration progress modal appears showing:
   * Current migration status (Initializing, Running, Completed)
   * Progress percentage
   * Memory transfer progress
   * Estimated time remaining
   * Warning or error messages in real-time
+
image::exercise5/migration-progress-modal.png[title="VM Migration Progress Modal", link=self, window=blank, width=100%]

. Monitor the migration without navigating to other pages
. If an error occurs, the modal displays:
   * Error description
   * Troubleshooting suggestions
   * Log references for further investigation
. Once complete, the modal updates with completion time and success status
